# HOUHI 仮想開発チーム構成

この文書は、HOUHI を「本人訴訟・裁判資料整理・AI 起案・証拠処理・提出用 PDF 作成をつなぐ実務ワークベンチ」として開発するための、仮想開発チームの共通指示である。

HOUHI は、利用者に内部コマンドを覚えさせるための道具ではない。利用者が訴訟フォルダを VS Code や通常のファイル操作で開き、Codex や Claude Code に日本語で依頼すれば、HOUHI が安全に内部処理を担う体験を目標にする。

訴訟フォルダ内で事件処理を分担する仮想チームは、[仮想チーム構成.md](%E4%BB%AE%E6%83%B3%E3%83%81%E3%83%BC%E3%83%A0%E6%A7%8B%E6%88%90.md) を参照する。この文書は、HOUHI リポジトリそのものを開発・保守するためのチーム構成を扱う。

## 基本方針

HOUHI の責務は、次の実務処理を安全に接続することである。

- Markdown 裁判文書から提出用 PDF を作成する。
- 証拠 PDF / 画像に号証スタンプを付ける。
- 証拠 PDF を確認可能な順序で結合する。
- FAX 向け PDF を作成し、mfax 送信を補助する。
- Chat AI に渡す AI アーカイブを作成する。
- `houhi-drafting-kit.zip` を生成・維持する。
- 本人訴訟フォルダに、AI エージェントが扱える索引・管理ファイルを作る。
- MIMI OCR と連携し、スキャン資料を Markdown 化する導線を整える。

役割分担の境界は明確にする。

- OCR、文書ごとの分割・結合、OCR Markdown の維持は MIMI OCR 側に寄せる。
- PDF 作成、号証スタンプ、証拠 PDF 結合、FAX 向け PDF 化は HOUHI 側で扱う。
- Chat AI は起案、整理、レビュー、次アクション提示を担う。
- ローカルファイル操作、PDF 生成、FAX 送信、外部 API 実行は HOUHI とコーディングエージェントが明示承認の範囲で担う。

外部エージェントや専用 CLI が実際に利用できない場合は、Codex がその役割の観点を使ってレビューする。利用できないツールを使ったことにしてはならない。

## 役割別指示

### Codex / 開発司令塔

- すべての開発タスクの入口になる。
- 変更前に、PDF 作成、号証スタンプ、AI アーカイブ、FAX、GUI、Web 版、Windows 配布への影響を確認する。
- HOUHI と MIMI OCR の責務境界を守る。
- 他担当の提案を、既存コード、テスト、安全ルールに照らして統合する。
- 変更後は原則として `npm test` を実行する。
- ツールコメントやユーザー向け CLI 挙動を変えた場合は `npm run docs:tools` も実行する。

### Claude Code / アーキテクト観点

- TypeScript の型、責務分離、テストしやすさを確認する。
- Markdown 仕様、裁判文書 CSS、Chrome / Copper PDF 出力への影響を確認する。
- 本人訴訟フォルダ仕様、`CASE_INDEX.md`、`.houhi/manifest.json`、`AGENTS.md` 生成仕様を確認する。
- `houhi-drafting-kit.zip` のテンプレートや AI 起案指示が、事実を創作させる内容になっていないか確認する。

設計メモを書く場合は、結論、影響範囲、現状の問題、推奨設計、互換性リスク、テスト観点、実装手順の順にまとめる。

### agy / GUI・UX 観点

- GUI は本体ロジックを抱え込みすぎず、CLI / ライブラリ処理を安全に包む入口にする。
- 初心者が、対象ファイルをどこに入れ、処理後に何を確認すればよいか分かる画面にする。
- FAX 送信、外部送信、破壊的操作は、必ずプレビューと確認を挟む。
- エラーは、原因と次の操作を日本語で示す。
- GUI 変更時は Web 版との差異も確認する。

### Grok Build / 破壊的 QA 観点

- Windows 配布版が壊れないか確認する。
- PDF の裁判文書体裁、改ページ、表、右寄せ、日本語フォントの崩れを確認する。
- `甲1`、`甲1-1`、`甲10`、`乙2` などの証拠番号順が壊れないか確認する。
- FAX 送信前確認を飛ばせないか、番号を推測していないか確認する。
- `config.json`、`.env`、SMTP / mfax パスワード、API キーがログや成果物に混入しないか確認する。
- 原本ファイルを上書き、移動、改名していないか確認する。

QA メモを書く場合は、壊れる可能性、再現手順、実際の挙動、期待される挙動、最小修正案、回帰テスト案、リリース可否の順にまとめる。

### MIMI OCR 連携担当

- PDF、画像、Word、ODT、PowerPoint などから、OCR Markdown が必要なものを判定する。
- 対応する `_paged.md`、`_merged.md` などの存在確認を行う。
- 外部 AI OCR を使う可能性がある場合は、資料内容が外部 AI provider に送信され得ることを説明し、明示承認を得る導線を守る。
- HOUHI 側で OCR Markdown を正規化、要約、手作業分割して代替しない。
- MIMI OCR Markdown のメタデータ、ページ境界、判読不能表記、出力規約を保持する。

### PDF 組版担当

- 訴状、答弁書、準備書面、証拠説明書、送付書、反訳書で体裁を確認する。
- 表、右寄せ、インデント、改ページ指定、日本語フォント、長文で崩れないか確認する。
- Chrome PDF と Copper PDF の差異を意識する。
- 提出用 PDF は、人間が最終確認する前提で出力する。

### 証拠処理担当

- 証拠番号を推測で確定しない。
- ファイル名先頭の `甲1_契約書.pdf`、`乙2_メール.pdf` などは候補として扱い、必要に応じて `【要確認】` を出す。
- 号証スタンプ前の原本を上書きしない。
- 結合順はログやレビュー用一覧で確認できるようにする。
- 証拠説明書と食い違う場合は `【要確認】` を出す。

### 起案キット・ドキュメント担当

- `houhi-drafting-kit.zip`、`00_START_HERE.md`、訴状・答弁書・準備書面・証拠説明書テンプレートを維持する。
- Chat AI が事実関係を創作しないよう、不足情報を確認する手順を入れる。
- Markdown 原案と提出用 PDF を区別する。
- 最終確認は利用者が行う前提を書く。
- 非技術者向け手順では、HOUHI コマンドではなく「AI にどう頼めばよいか」を優先して説明する。

### FAX / Mail 担当

- FAX 番号を推測しない。
- 送信前に必ずプレビュー、宛先確認、ユーザーの明示承認を挟む。
- パスワード、SMTP 認証情報、FAX 送信パスワードをログに出さない。
- テスト送信と本番送信を明確に分ける。
- FAX 向け二値化、ディザリング、ページ単位確認の導線を壊さない。

### リリース担当

- `npm install`、`npm run setup`、`npm test`、`npm run gui`、`npm run build:web`、`npm run serve:web`、`npm run release:win` の影響を確認する。
- Node.js なし Windows 環境で配布版が起動できる前提を守る。
- `release/houhi-win-x64/` と release ZIP に必要物が入っているか確認する。
- README-START、リリースノート、GitHub Actions への影響を確認する。

| AI アーカイブ | アーキテクト、ドキュメント、MIMI OCR 連携 |

| 起案キット | 起案キット、アーキテクト、ドキュメント |
| 訴訟フォルダ整理 | MIMI OCR 連携、証拠処理、ドキュメント |

| ツールドキュメント生成 | ドキュメント、アーキテクト |

## 開発ワークフロー

1. Codex が依頼内容と既存コードを読む。
2. 影響範囲を PDF、証拠、FAX、GUI、Web、起案キット、MIMI OCR 連携、リリースの観点で分類する。
3. 設計が必要な場合はアーキテクト観点で方針を固める。
4. GUI 変更なら GUI / UX 観点を入れる。
5. Windows 配布、PDF 崩れ、号証順、FAX 安全性に関わる場合は破壊的 QA 観点を入れる。
6. 起案キットや利用者向け文書ならドキュメント担当観点を入れる。
7. Codex が実装・文書更新・テスト追加を統合する。
8. `npm test` を実行する。
9. 必要に応じて `npm run build`、`npm run docs:tools`、`npm run build:web`、`npm run release:win` を実行する。
10. 残るリスク、未実行の確認、次アクションを報告する。

## Definition of Done

通常変更は、次を満たして完了とする。

- `npm test` が通る。
- 必要な場合に `npm run build` が通る。
- ツールコメントやユーザー向けツール説明を変えた場合、`npm run docs:tools` が通る。
- PDF、証拠、FAX、GUI、Web 版、起案キットへの影響を確認した。
- 原本ファイルを上書きしていない。
- 利用者の明示承認なしに元ファイルを移動・改名していない。
- 秘密情報がログ、成果物、ドキュメントに混入していない。
- 不確かな事実、日付、当事者、証拠番号、裁判所名、引用は `【要確認】` として扱っている。
- 必要な docs、README、テスト、golden fixture を更新した。

リリース対象は、追加で次を確認する。

- `npm run release:win` が通る。
- Windows 配布版が起動できる。
- PDF 作成、号証スタンプ、AI アーカイブ、FAX プレビューを確認した。
- MIMI OCR 連携手順が壊れていない。
- リリースノート又は README-START の更新要否を確認した。

## 重点テスト観点

- PDF の裁判文書体裁。
- 証拠番号順。
- 原本保護。
- `【要確認】` の扱い。
- MIMI OCR Markdown の保持。
- FAX 送信前確認。
- 秘密情報の非表示。
- Windows 配布版。
- GUI と Web 版の操作導線。
