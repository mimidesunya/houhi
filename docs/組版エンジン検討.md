# 組版エンジン検討

2026-11-26 に、houhi の PDF の組版を1つのエンジンに寄せられるかを見るため、Typst で3つの文書を試作し、デスクトップの Chrome エンジンで作った PDF と並べて比べた。あわせて Copper PDF を手元やブラウザで動かす案も公式の情報で調べた。エンジンの置き換えはしておらず、この文書に書くのは比べた事実と推奨までで、決めるのはユーザーである。

## 1. 今の4経路と問題

| 経路 | 場所 | 組版と PDF の作り方 |
| :--- | :--- | :--- |
| Web 版 | `src/web/app.ts` | iframe の中で paged.js 0.4.3 が頁を割ってプレビューし、PDF はブラウザの印刷（`frameWindow.print()`）で作る |
| デスクトップ Chrome（既定） | `src/lib/pdf_converter_chrome.ts` | ヘッドレス Chrome で paged.js を走らせ、DevTools の `Page.printToPDF` で PDF にする |
| Copper PDF | `src/lib/pdf_converter_copper.ts` | CTIP で HTML を公開サーバー `ctip://cti.li/` に送り、`output.pdf.version=1.4A-1`（PDF/A-1b）の PDF を受け取る。書類が外へ出る |
| Word | `src/lib/docx_converter.ts` | `court_document_model.ts` のモデルから docx を作る（PDF は作らない） |

PDF を作る3経路は、Markdown から HTML への変換（`src/base/court_markdown.ts`）と体裁（`src/base/style.css`）を共有しているが、組むのはそれぞれ別のエンジンなので、経路ごとの差を見つけるたびに個別に手当てしている。2026-11-25 の「Web 版の印刷で証拠説明書の表の行が消える」不具合はその典型で、paged.js が画面で頁を割ったあと、印刷のときにブラウザがもう一度組み直したために、頁末の行が見えない段へ移って消えた。`src/lib/paged_tables.ts` で手当てはしたが、画面と印刷で2回組むという構造は残っている。

測る途中で、エンジンの選択とは別に、今の Chrome 版の出力に次の食い違いがあることが分かった。いずれも数値は baseline の PDF の実測である。

- ルビが本文と同じ 12pt で出る。`src/convert_to_pdf.ts` の `CHROME_PAGE_NUMBER_STYLE` が `html[data-houhi-pdf-engine="chrome"] body *` に `font-size: 12pt` を指定しており、これが `style.css` の `rt { font-size: 50%; }` より強いためで、準備書面の「｜契約成立《けいやくせいりつ》」は、ルビが 12pt で8字分の幅になり、親字が「契　約　成　立」と広げられ、その行が通常より 4.6pt 下がっている。
- 当事者欄の電話の行の前に1行分の空きが入る。`table.info { margin-bottom: 1.618em; }` が `p.contact` の前にも効くためで、訴状では「原告　甲野　太郎」の基線が 288.0pt、「電話 000-0000-0000」が 327.8pt と2行分離れている。`docs/Markdown仕様書.md` は「氏名の直後に間を空けずに出します」としている。
- paged.js は、自動の改頁の後でも頁の頭の余白を残す。準備書面の2頁目の「以上」は、頁の1行目より1行下（132.0pt）に出ている。また頁番号の基線が、7頁の証拠説明書では 807.8pt から 805.5pt まで少しずつずれている。
- Chrome 版の字は、指定の先頭の `NotoSerifJP-Regular` という名の字がこの PC に無い（Windows にあるのは可変フォントの `NotoSerifJP-VF.ttf` で、ファミリー名は「Noto Serif JP」）ため、MS 明朝で組まれている。

## 2. 比べた方法

### 入力

- 訴状: `src/templates/訴訟.訴状.md`
- 準備書面: `src/templates/訴訟.準備書面.md`
- 長い証拠説明書（40行、7頁）: `scripts/experiments/typst/make_long_evidence.js` が作る表（作成年月日はすべて和暦、立証趣旨の長い行を5行に1行混ぜる）

補助に、比べる相手の baseline（8節）にある38文書（テンプレート36件と sample.md、長い証拠説明書）、禁則の試験（12例）、頁より高い行と枝番12行を入れた表の試験も組んだ。

### 版と環境

| 項目 | 内容 |
| :--- | :--- |
| 比べる相手 | houhi の Chrome エンジン（Chrome 157.0.8103.79 headless ＋ paged.js 0.4.3）。baseline フォルダの PDF |
| Typst CLI | 0.15.1（github.com/typst/typst の Releases、`typst-x86_64-pc-windows-msvc.zip`。SHA-256 は Releases の digest と一致） |
| typst.ts | `@myriaddreamin/typst-ts-web-compiler` 0.8.0-rc4（npm の rc タグ。中の Typst は 0.15.1）と 0.7.0（latest タグ。中の Typst は 0.14.2） |
| 字 | MS 明朝（`msmincho.ttc`）、游明朝（`yumin.ttf`）、Noto Serif JP（Windows の `NotoSerifJP-VF.ttf` と、notofonts/noto-cjk の `Serif/SubsetOTF/JP/NotoSerifJP-Regular.otf`。後者は git の blob ハッシュが一致） |
| 測る道具 | Windows 11 Pro、Node 24.22.1、Python 3.12 ＋ PyMuPDF 1.26.4、worktree の pdfjs-dist 4.10.38 |

### Markdown から Typst への変換

試作の変換（`md2typ.js` 254行と、体裁を写した前置き `court.typ` 87行）は、Markdown を自分で解釈せず、houhi の `court_markdown.ts` が出す HTML（dist の写し）をクラスで読み、`style.css` の寸法を Typst の指定へ写す。こうすると、見出しと番号の判定、当事者欄の項目表の列幅、証拠説明書の列幅（colgroup の百分率）や枝番の結合が houhi と同じになるので、エンジンの差だけを比べられる。

行送りは、CSS の `line-height: 1.618em` に合わせて1行の箱を 1.618em にした（`top-edge: 1.168em`、`bottom-edge: -0.45em`。MS 明朝の ascent 0.859em に行間の半分 0.309em を足した値）。段落の間と塊の間は0にし、CSS の margin だけを弱い `v()` で入れたので、隣り合う margin は大きい方が残り、頁の頭では消える。番号付きの階層の字下げは、Chrome 版の PDF の実測に合わせた。ほかに `linebreaks: "simple"`（Chrome と同じ逐次の折り返し）、`cjk-latin-spacing: none`（和欧間の四分アキを入れない。Chrome 版も入れていない）、`overhang: false`（行頭・行末の約物や「-」を版面の外へはみ出させない）を指定した。

### 比べ方

1. 頁ごとの本文を pdfjs で取り、NFKC・空白除去のうえ、並び順を無視して字が同じかを見た（PDF の中の書き出し順はエンジンによって違う）。
2. PyMuPDF で同じ基線の字を1行にまとめ、行の字の並び・頁・左端の位置を、difflib で対応を取って突き合わせた。
3. 頁や一部を PNG にして並べ、目で見た。
4. 時間は、Typst は7回、Chrome エンジンは3回組んだ中央値を取った（いずれもプロセスの起動を含む）。

### 禁則の試験（12例、素の Chrome の印刷と Typst）

1行目は1字下げなので36字が入り、37字目以降が2行目になるように作った。

| 例 | Chrome | Typst |
| :--- | :--- | :--- |
| A 句点が2行目の頭に来る | 1行目を35字にして「あ。」を2行目へ | 1行目に36字と「。」（半角に詰める） |
| B 閉じかぎが2行目の頭に来る | Aと同じく追い出し | Aと同じく追い込み |
| C 開き括弧が1行目の末尾に来る | 括弧を2行目へ（全角） | 括弧を2行目へ（半角に詰めて天付き） |
| D 促音が2行目の頭に来る | 「った」で始まる2行目を許す | 「あった」と前の字ごと送る |
| E 長音が2行目の頭に来る | 「ーた」で始まる2行目を許す | 「あーた」と前の字ごと送る |
| F 三点リーダーが行をまたぐ | 分けない | 分けない |
| G 数字が行をまたぐ | 分けない | 分けない |
| H 「）。」が2行目の頭に来る | 追い出し | 追い出し（同じ） |
| I 「、「」」、（）、『』。」の連続 | 1行目33字 | 1行目40字（連続を詰める） |
| J 中黒が行頭に来る | 追い出し | 追い出し（同じ） |
| K 欧文の語が行をまたぐ | 語の前で折り返す | 同じ |
| L 句点がちょうど1行目の末尾 | 1行に収まる | 同じ |

Typst のこの扱いは、Typst のソース（`crates/typst-layout/src/inline/shaping.rs` と `line.rs`）で確かめると、JIS X 4051・JLReq に沿って約物の幅を詰めるもので、詰めてよい量（字幅の半分）は固定されており、設定で切る口が無い。試作でも `overhang: false`、`lang` を `en`・`zh` に替える、のいずれでも結果は変わらなかった。行頭の小書きの仮名・長音を許さないのも同じで、変える設定は見当たらなかった。

### 38文書での行の一致

baseline フォルダの38文書を試作の変換で組み、Chrome 版で行末まで詰まった本文の行（両端揃えで折り返した行）320行を数えると、Typst 版に字の並びが同じ行があるものは284行（88.8%）だった。一致しなかった36行は、22行が折り返し位置の近くに約物か小書きの仮名がある行、8行が行の途中に「。）」「（以下「」のような約物の連続がある行、残る6行は同じ段落で前の行がすでに違っていたための波及で、いずれも上の約物の扱いの差で説明がつく。ただし試作の変換は、改頁（`### -- --`）、送付書の 10.5pt、見出し付きの一般の表を扱っていないので、その2文書（保有個人情報利用停止請求書、送付書）は頁数が違った。この2件はエンジンの差ではなく変換の未対応による。

MS 明朝は Windows に付く字で、ウェブ版の配布物に入れて配ることはできない（再配布できない字である、という一般的な理解による）。ブラウザで MS 明朝を使うなら、利用者の PC から字を読ませる必要があり、Chromium の Local Font Access API（`queryLocalFonts()`）が候補になるが、試していない。

0.7.0（latest タグ、中の Typst は 0.14.2）では、同じ前置きでも番号を入れた箱の基線の扱いが違い、訴状と準備書面で番号付きの行の本文が 5.4pt 下にずれた。試作の前置きは Typst 0.15 を前提にしているので、ブラウザでも 0.8 系が要る。

## 4. Typst の長所と短所

### 長所

- 同じ入力から、CLI、Node の WASM、ブラウザの WASM のどれで組んでも同じ PDF ができた。Web 版でもデスクトップでも、画面で組んでから印刷で組み直すという段が無くなるので、2026-11-25 の不具合のような「プレビューと PDF が違う」種類の不具合は構造の上で起きない。
- 頁割りと字詰めを、Chrome 版にほぼ合わせられた。3文書で頁数と頁ごとの字は全部一致し、行の一致は 268/271 行で、違いは約物と小書きの仮名の扱いと、Chrome 版のルビの不具合によるものに限られた。
- 表頭の繰り返し、行を分けない指定、rowspan、列幅を、Typst の表の機能だけで書ける。paged.js の補い（`paged_tables.ts`）のような、組版エンジンの外からの手当ては要らなかった。
- 組む速さは、Chrome エンジンの1文書 0.63〜0.9 秒に対して、CLI で 0.03〜0.13 秒、ブラウザで 0.01〜0.2 秒（WASM の初期化 0.1〜0.3 秒を除く）だった。Chrome を探して起動する必要も無い。
- PDF/A-1b、PDF/A-2b などを指定して出力でき、Copper の `1.4A-1` に当たる出力を手元で作れる。Chrome の印刷では作れない。
- PDF は Chrome 版より 9〜23% 小さかった。
- Typst も typst.ts も Apache-2.0 で、外部のサーバーに書類を送らない。

### 短所

- 約物の詰め（行末の句読点の追い込み、約物の連続の詰め、行頭の開き括弧の天付き）と、行頭の小書きの仮名・長音の禁止が、Typst の中で決まっていて切れない。このため1行の字数は、約物を含む行で Chrome 版と違うことがあり、38文書では行末まで詰まった行の 11.2% が違った。JIS X 4051 に沿った組み方ではあるが、今の PDF と1字単位で同じにはならない。Copper の新しいエンジン（FolioJet）も README で JLReq の禁則と行の調整を掲げているので、Chrome 版より Copper 版に近い組み方になるのかもしれないが、Copper では試していない（推測）。
- ルビの機能が無く、試作は親字の上に置くだけである。親字より長いルビや熟語ルビをきちんと組むには、関数を書き足すか、Typst Universe のパッケージを使う必要がある。
- ブラウザで読む物が brotli でも約 12MB あり、paged.js の 0.5MB に比べて大きい。初回の読み込みは回線しだいで数秒かかる（推測）。キャッシュが効く2回目以降は速い。
- MS 明朝をブラウザで使えないので、Web 版とデスクトップで同じ字にするには、Noto Serif JP などの配れる字に揃えるか、利用者の PC の字を読ませる仕組みが要る。
- Typst は 1.0 前で、版が上がると組み方が変わりうる。実際に 0.14.2 と 0.15.1 で同じ前置きの結果が違った。版を固定し、今回の行の比較の道具で回帰を見る必要がある。typst.ts の PDF/A 対応は、まだ rc の 0.8.0-rc4 にしか無い。
- `style.css` を Typst の前置きに写した2つ目の体裁ができる。Copper の経路を残すなら、CSS と Typst の両方を保つ手間がかかる。
- デスクトップで CLI を同梱すると `typst.exe` が 52.5MB（zip で 22.5MB）、Node のネイティブ版（`@myriaddreamin/typst-ts-node-compiler` の win32-x64）が展開して 56.1MB 増える。WASM を Node で使えば 30MB で済む。

## 5. Copper を手元・ブラウザで動かす案

公式の情報（copper-pdf.com、zamasoftnet の GitHub）で分かったことは次のとおりで、手元で Copper を動かす試験はしていない。

### 手元で動かす

| 項目 | Copper PDF 3.2.34（今の製品） | FolioJet（COPPER 4 のエンジン） |
| :--- | :--- | :--- |
| 形 | サーバー製品（copperd）。CTIP と REST で受ける | ライブラリ（github.com/zamasoftnet/foliojet）。README に「COPPER 4 の組版エンジン」「2026年に書き直してオープンソース化」とある |
| ライセンス | 正規 165,000円。試用90日（すかし入り）。インストール後は機能限定版（無料、期限なし、すかし無し、機能制限あり。制限の中身はページに無く、PDF/A が使えるかは分からない）。個人・非商用は無償ライセンスあり | Apache-2.0 |
| Java | サーバーと copper コマンドは Java 8 以降、REST とウェブ画面は Java 17 以降 | Java 21（Gradle の toolchain） |
| 配布の大きさ | Windows 用 zip 43.7MB（JRE なし）、Temurin 21 同梱の zip 92.5MB（いずれもダウンロードの Content-Length）。Docker イメージ `ghcr.io/zamasoftnet/copper-pdf:3.2.34` は圧縮で 315.7MB（Noto Sans JP / Serif JP 同梱） | GitHub に Releases は無く、5つのリポジトリ（cti.java、html-balancer、pdfg2d、zstream、foliojet）を並べて Gradle でビルドする。大きさは分からない |
| PDF/A | `1.4A-1` は PDF/A-1b（FolioJet の手引き `docs/manual/contents/4050_output.md` による） | 同じ指定ができる（手引きに 1.4A-1〜2.0A-4 などの一覧） |

Copper 3.2 を手元のサーバーとして動かすだけなら、houhi 側は `config.json` の `copper.serverUri` を手元に向けるだけで、書類は外へ出なくなる。ただし利用者の PC ごとに Java のサーバー（92.5MB 程度）を入れて動かしておく必要があり、Web 版では使えない。FolioJet は Apache-2.0 なので、デスクトップ版に Java ごと組み込む道はあるが、今は手でビルドするしかなく、CTIP のサーバーとして動かせるかは README からは分からない。

### ブラウザで動かす

- TeaVM: 公式の対応表（teavm.org/jcl-report）で、`java.awt`、`java.awt.geom`、`java.awt.font`、`java.awt.image`、`javax.imageio`、`javax.xml.parsers` が対応外である。FolioJet は `java.awt` を import するファイルが182、組版の下の pdfg2d（Graphics2D を PDF に写すライブラリ）が156あり（GitHub のコード検索の件数）、Batik や Saxon にも依存するので、TeaVM で動かす見込みは無いと判断した。
- CheerpJ: 公式ページは CheerpJ 5.0 で Java 8・11・17・21 に対応（25 はプレビュー）し、AWT と Swing を HTML と canvas で描くとしている。理屈の上では FolioJet（Java 21）を動かせる可能性があるが、試していない。ライセンスは、組織で使う製品なら Small Business（月 £100／開発者）か Enterprise（見積もり）で、自前のサーバーから配るには追加の費用（Small Business で年 £5,000）がかかる。無償の枠は、個人や一人会社の公開ソフト、オープンソースで、いずれも CheerpJ の CDN から読み込み「Built with CheerpJ」を表示する条件である。読み込みの大きさは公式ページに無く、分からない。FolioJet が使う brotli4j はネイティブのライブラリを読むので、その部分はブラウザでは動かないと考えられる（推測）。

## 6. Chrome ＋ paged.js を残す案

今の経路を残す場合、第1節の食い違いのうち、ルビの大きさ（`CHROME_PAGE_NUMBER_STYLE` の `body *` から `rt` を外す）と、電話の行の前の空き（当事者欄の項目表の後ろに連絡先が続くときは表の下の余白を0にする）は、それぞれ数行の修正で直せる見込みである。新しい依存も新しい体裁の写しも要らず、Copper と同じ HTML/CSS を使い続けられるのが利点である。

一方で、Web 版の PDF はブラウザの印刷に頼るので、画面で組んだ頁割りと印刷で組み直した頁割りの食い違いは、今後も `paged_tables.ts` のような補いで1件ずつ防ぐことになる。paged.js は 0.4.3 で、表の頁またぎの補いも houhi 側で持ち続ける。デスクトップでは Chrome の起動を含めて1文書に 0.63〜0.9 秒かかり、PDF/A は出せない。

## 7. 推奨

Typst を、Web 版とデスクトップ Chrome の2経路をまとめる組版エンジンの第一候補として推す。理由は、同じ PDF を CLI でもブラウザでも作れることが試作で確かめられ、Web 版の印刷で組み直す段が無くなること、頁割りと行送りを今の Chrome 版に合わせられたこと、PDF/A を手元で出せるので Copper の公開サーバーに頼る理由の一つが無くなること、の3つである。

ただし、移る前にユーザーが決めておくべきことが2つある。1つは約物の詰めと行頭の小書きの仮名の扱いで、Typst では切れないので、約物を含む行の字数が今の PDF と変わることを受け入れるかどうかである。もう1つは字で、Web 版で MS 明朝を使えないので、Noto Serif JP などに全経路を揃えるか、Web 版だけ字が違うことを認めるかを決める必要がある。

Copper は、FolioJet が Apache-2.0 になったことで手元で動かす道が開けたが、ブラウザで動かす見込みは CheerpJ に頼るしかなく、ライセンスと読み込みの大きさが分からないので、今の段階では Web 版の答えにならない。公開サーバーへの送信をやめたいだけなら、Typst への移行とは別に、手元の Copper サーバーを使う設定を勧める道もある。

移行しない場合でも、第1節のルビの大きさと電話の行の前の空きは、Chrome 版の出力の食い違いとして直す価値がある。

### 移行するときの手順と手間の見積もり

手間はいずれも推測で、1人の開発者の日数である。

1. 決めること（約物の扱い、字、PDF/A の版）を決める。
2. HTML から Typst への出力を作る（4〜6日）。試作と同じく `court_markdown.ts` の HTML を入力にし、Markdown仕様書の全記法（7段の階層、目次は Typst の `outline()`、改頁、区切り線、空行、横置きの頁と左の短辺の頁番号、小さい字、送付書の 10.5pt、見出し付きの一般の表、画像、下線、行内改行）を扱う。のちに `court_markdown.ts` を、HTML と Typst の両方を出せる中間の木に分けると、二重に解釈しなくて済む。
3. 前置き（`court.typ`）を `style.css` の全規則に合わせ、7段の番号の位置、目次、横置きを実測で詰める（2〜3日）。
4. デスクトップに Typst を選べるエンジンとして足す（1〜2日）。既定は Chrome のままにし、WASM を Node で使うか CLI を同梱するかを決める。
5. baseline の38文書で、今回の道具（頁ごとの字、行の並び・位置）を回帰の試験にして、Chrome 版との差が約物の扱いだけになるまで詰める（2〜3日）。
6. Web 版で、WASM を Worker で動かして PDF を直接作り、プレビューは pdf.js（今も依存にある）で頁を描く（3〜5日）。字の読み込みとキャッシュも作る。
7. 既定のエンジンを Typst に替え、paged.js と `paged_tables.ts`・`paged_toc.ts` を外し、文書と試験を直す（2〜3日）。

合計は 15〜25日ほどと見積もる（推測）。

```sh
# 字を替えるとき: --font-path "$TYPST_WORK/fonts/noto-otf" --input "font=Noto Serif JP"
# PDF/A-1b: --pdf-standard a-1b
```

## 9. Web 版の Chromium と WebKit の差

Web 版のプレビューに Noto Serif JP の Web フォントを入れた後、テンプレート36件と sample.md を Chromium（Playwright 1.58.2 の chromium-1208）と WebKit（同じく webkit-2248）で組み、頁ごとの本文を比べた（`tests/web_cross_browser.test.js`）。37件とも頁数と本文（欠けも重なりもない）は一致したが、12件で改頁の位置がずれ、WebKit のほうが頁の末に1〜3行（最大87字）多く入った。

原因は行の箱の高さの丸めである。行送り 1.618em（12pt で 25.888px）を、Chromium は丸めずに使うが、WebKit は画面の画素に丸め、Windows の 125% 表示では 25.6px（0.8px 刻み）になった。Mac の Retina の Safari では 0.5px 刻み、Linux の WebKit では 1px 刻みになるはずで、行送りを 26px にしても Windows の WebKit は 25.6px に丸めた。どの刻みでも割り切れる行送りは 4px の倍数（24px・28px）しかなく、今の体裁（1頁34行）のまま揃える方法は見つからなかった。ルビのある行の高さの増え方も、Chromium の +5px に対し WebKit は +11px で違う。

試験は、頁数と本文が同じことを確かめ、改頁の位置のずれは5行分（200字）まで許す（手元では最大87字、GitHub Actions の windows-latest では160字だった）。Typst のように PDF を直接作る経路なら、ブラウザの組版を通らないので、この差は無くなる。
